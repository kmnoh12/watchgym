| 3. 체크포인트·예외 경계 보강 | 청크와 상태 저장 성공 구분, 실패 반환 전달, 미참조 청크 복구 또는 작은 저장 저널, 센서·타이머 경계의 전환 보류 처리. | 저장 단계 사이에서 종료시켜도 확정 기록 보존, 미완료 상태 명시, 잘못된 ACK 없음. | 원본 삭제·덮어쓰기, 중복 적용, 재시작 반복, 저장 지연 악화 시 해당 변경 되돌림. |
| 4. 별도 용량 변경 | 실제 지원 ABI 확인 후 폰 OTA 변형에만 ABI 제한. 디버그 지원 ABI 유지. | 목표 기기 설치·카메라 초기화 정상, 배포 파일 선택 정확, 크기 재측정. | 기존 지원 기기가 설치·업데이트할 수 없으면 기존 ABI 구성 복원. |
| 5. 표적 실기기 관측 | 개인 기기에서 중단·연결 끊김·화면 꺼짐·업데이트 복구 관측. | 아래 지표를 버전별로 보고하고 모든 사고 원인을 추적 가능. | 확정 기록 유실·중복 확정·운동 중 앱 교체가 한 번이라도 발생하면 배포 확대 중단. |

설치 차단은 버튼 비활성화만으로 끝내면 안 된다. 최소한 각 기기에서 운동 소유자와 설치 경로가 **같은 동기화 경계에서** 상태를 판단해야 한다. 원격 설치 요청은 보존하되, 워치가 실제 설치 직전에 자신의 운동 상태를 다시 확인해야 한다. 워치 미응답을 “워치도 유휴 상태”로 해석해서는 안 된다.

OS 설치 확인을 기다리는 동안에도 새 운동이 시작될 수 있으므로, 설치 트랜잭션이 진행 중이면 새 운동 시작을 보류하거나 설치를 취소하도록 해야 한다. 이미 OS에 넘긴 설치를 앱이 언제든 취소할 수 있다고 가정하지 않는다.

체크포인트는 우선 **세트 완료·사용자 수정·명령 적용을 저장 성공 뒤 확정하는 규칙**부터 강화한다. 진행 중 원본은 잠정적으로 1초 이내의 미저장 구간을 목표로 검토하되, 그대로 main thread의 `fsync` 빈도를 높이지 않는다. 순서를 보장하는 제한된 쓰기 큐와 저장 완료 지점을 함께 다루고, 저장장치가 느리면 사용자에게 저장 지연을 표시한다.

지금 보류할 일은 서비스 전체 분리, 전면 DB 이전, 큰 파일의 일괄 분할, 검출기·옛 경로 일괄 삭제, 모델 교체다. 네이티브 크래시가 확인되거나 저장 지연이 반복 측정되면 해당 원인에 한해 다음 변경을 선택한다.

**4. 앱 크기와 크래시는 별도 문제다**

기존 `phone/build/outputs/apk/ota/phone-ota.apk`와 워치 OTA APK의 ZIP 목록을 읽었다. 아래는 새 빌드 결과가 아니다.

| 항목 | 확인값 |
|---|---:|
| 폰 OTA APK | 60,607,320 bytes = **57.80 MiB** |
| 워치 OTA APK | 1,351,831 bytes = **1.29 MiB** |
| 폰 네이티브 라이브러리, ABI 4종 합계 | **43.99 MiB** |
| 폰의 arm64 이외 ABI 합계 | **33.90 MiB** |
| 이 항목만 제거한 단순 계산상 폰 크기 | **약 23.90 MiB** |

라이브러리는 이 APK에서 ZIP 압축 없이 저장돼 있어 제거분 계산이 직접적이다. 실제 재빌드 크기는 정렬·서명·다른 변경 때문에 달라진다. 브리프의 “약 40MB 감소”는 이 산출물 기준으로는 과대 추정이다.

폰 APK 수정 시각은 2026-10-18 01:17:42, 워치는 01:03:55다. `0cd2f39`의 01:49:26과 `e69de5d`의 02:01:27보다 앞선다. 이 APK로 최신 업데이트 흐름이 포함됐거나 설치 검증됐다고 주장할 수 없다.

현재 폰 Gradle에는 ABI 필터가 없고, 축소는 실제 OTA용 `ota` 빌드 타입에 켜져 있다. 일반 `release`에 동일 설정이 있다고 혼동하면 안 된다. 근거: [phone/build.gradle.kts:40](/Users/kmnoh/Documents/Default%20Project/워치짐/phone/build.gradle.kts:40).

ABI 제한의 효과는 다운로드량·설치 파일 공간·업데이트 준비 부담 감소다. 기기에서 사용하지 않는 ABI의 라이브러리를 제거한다고 실행 중 메모리가 그만큼 줄거나 네이티브 결함이 없어지지는 않는다. Android는 대상 기기에 맞는 ABI를 선택한다. [Android ABI 문서, 확인 2026-10-18](https://developer.android.com/ndk/guides/abis?hl=en)

개인용 arm64 제한은 **실제 폰의 지원 ABI를 확인한 뒤** 선택할 수 있다. 이번에는 기기를 조회하지 않았다. 32비트 ARM 기기와 x86 계열 환경을 지원할 계획이라면 무조건 제한하면 안 된다. 디버그에는 필요한 에뮬레이터 ABI를 유지하되, 디버그 성공을 축소된 OTA APK의 카메라 초기화 성공으로 대신하지 않는다.

현재 OTA는 APK 하나를 `base.apk`로 설치하는 구조다(`U/OtaInstaller.kt:58–68`). 상용화 때 AAB를 택하면 Play가 기기별 APK를 제공할 수 있지만, AAB를 현재 GitHub OTA 주소에 그대로 넣는 방식은 아니다. 자체 ABI별 APK 배포도 manifest 선택과 호환성 검사가 필요하다. [Android App Bundle 문서, 확인 2026-10-18](https://developer.android.com/guide/app-bundle)

프로세스만 나누면 APK 크기는 거의 그대로다. 반대로 기능을 별도 모듈로 옮겨도 같은 APK에 포함하면 설치 크기 감소가 보장되지 않는다.

프로세스 분리는 네이티브 장애 격리에 유효할 수 있지만 저장 복구를 대체하지 않는다. 현재 preferences와 정적 lock을 그대로 두고 `android:process`만 추가하면 안 된다. SharedPreferences는 다중 프로세스 사용을 지원하지 않는다. 카메라를 분리하더라도 세션 저장은 한 소유자에게 남기고, 요청 ID·결과·프로세스 사망을 명시적으로 처리해야 한다. [SharedPreferences 계약, 확인 2026-10-18](https://developer.android.com/reference/android/content/SharedPreferences)

**5. 검증 지표와 좁은 검증 순서**

“다시 켜졌으니 성공”으로 집계하면 사용자가 싫어하는 끊김이 숨겨진다. 복구 성공률과 운동 중 중단률을 별도로 측정해야 한다.

| 지표 | 정의 | 초기 수용 기준 제안 |
|---|---|---|
| 확정 기록 유실 | 저장 완료로 표시하거나 적용 ACK한 세트·수정 중 재시작 후 복구되지 않은 건수 | 주입 검증과 현장 관측에서 **0건**. 한 건이면 배포 확대 중단 |
| 진행 중 원본 손실·공백 | 마지막 지속 저장 샘플부터 종료 전 수신 샘플까지의 손실, 서비스 중단 중 미수집 시간을 구분 | 손실·공백을 숨기지 않음. 저장 중인 프로세스의 미저장 창은 잠정 1초 이내 목표 |
| 중복 확정 | 동일 세션·세트·attempt에 완료 기록이나 수정이 두 번 적용된 건수 | 재전송·ACK 손실·역순 수신에서 **0건** |
| 복구 지연 | 프로세스 종료→복구 진입, 복구 진입→조작 가능, 연결 복구→양쪽 합의까지 각각 측정 | 앱 복구 진입 후 조작 가능 p95 3초, 연결 복구 후 합의 p95 10초를 초기 목표로 검토 |
| 상태 불일치 | 양쪽이 같은 세션에서 세트·attempt·phase·휴식 revision에 합의하지 못한 시간 | 연결 단절 중 대기와 연결 후 불일치를 분리. 오래된 상태로 역행 0건 |
| 사용자 체감 중단 | 운동 세션 중 크래시·ANR·조작 불능·의도치 않은 홈 복귀가 한 번 이상 발생한 세션 비율 | 복구됐어도 실패로 집계 |
| 미처리 전송 | pending 항목 수, 최고 대기 시간, 재시도 횟수, 저장 실패 횟수 | 정상 연결 후 지속 증가 없음. 자동 삭제로 숫자를 낮추지 않음 |

목표 수치는 현재 달성값이나 OS 보장이 아니다. 특히 OS가 프로세스를 언제 다시 실행할지는 앱이 통제할 수 없으므로 “자동 복구 3초 보장”으로 표현하면 안 된다. 프로세스가 죽어 센서가 측정하지 못한 시간도 재계산으로 되살릴 수 없다.

최소 관측 자료는 양쪽 앱 버전, OS/API, 프로세스 실행 ID, 세션·세트·attempt ID, 명령 revision, 저장 완료 위치, ACK 상태, 종료 이유, 복구 결과다. 원본 영상·인증 정보는 진단에 넣지 않는다. 로컬 순환 로그와 사용자가 내보내는 묶음으로 시작하고, 상용 단계에서 동의 기반 수집을 검토한다.

후속 검증은 다음 순서가 적절하다.

1. 변경한 경계 하나의 테스트부터 수행한다. 종료 정책은 `WorkoutTerminationTest`, 설치 차단은 OTA 대상 테스트, 원본 저장은 청크 저장 실패·복구에 집중한 테스트로 나눈다.
2. 파일 기록 직후, 상태 저장 직전·실패 직후, 폰 저장 후 ACK 전, 워치 ACK 수신 후 정리 전에서 중단을 주입한다. 정상 `onDestroy()` 호출만으로 프로세스 사망을 흉내 내지 않는다.
3. 대상 실기기에서 작업 제거, 프로세스 종료, 명시적 강제 중지, 재부팅을 별도 시나리오로 확인한다. 화면 꺼짐·Bluetooth 단절·권한 거절·저장 실패도 해당 경계에 한해 추가한다.
4. 같은 기기·버전으로 먼저 2–4주 또는 30회 운동을 관측한다. 이는 초기 결함 발견 단계이며 상용 안정성 인증이 아니다. 이후 지원 기기·OS별로 범위를 넓힌다.

전체 테스트·전체 빌드를 매번 기본 게이트로 삼을 필요는 없다. 관련 단일 테스트와 변경 모듈 컴파일부터 시작하고, 설치 검증이 필요한 단계에서만 해당 배포 산출물을 준비한다.

실패 0회도 무고장 증명이 아니다. 독립적이고 같은 조건의 운동 세션이라는 이상적인 가정에서, 0회 실패를 관측했을 때 실패율의 단측 95% 상한은 대략 `3/n`이다. 100회 무실패는 약 3%, 300회는 약 1%, 3,000회는 약 0.1% 수준이다. 같은 사람·기기의 반복은 상용 사용자 집단을 대표하지 않으며, 한 운동의 세트 수를 독립 표본처럼 늘려 계산하면 안 된다.

센서 검출 정확도는 별도 지표다. 앱이 정상 동작했어도 횟수가 틀릴 수 있고, 앱이 재시작됐어도 이미 확정한 기록은 정확히 보존될 수 있다. 실제 횟수 오차를 크래시율과 섞지 않는다.

**6. 실패 상황별 기록 보존 절차**

| 상황 | 권고 절차 |
|---|---|
| 워치 서비스·프로세스 종료 | 마지막 유효 상태와 원본을 읽고 식별자·청크·시간축 검증 → 미완료 전송 재개 → 폰과 합의 → 측정 공백 표시. 복구 실패 시 원본을 유지한 복구 대기로 전환하고 같은 입력의 무한 재시작을 막는다. |
| 폰 프로세스 종료 | 활성 스냅샷·완료 수신 기록·명령 outbox를 복구하고 워치와 재조정한다. 새 세션을 만들어 덮어쓰지 않는다. 폰이 없던 동안 워치에 남은 현재 세트 기록부터 받아들일 수 있어야 한다. |
| 화면 닫기·작업 제거 | 기록을 폐기하지 않는다. 종료를 선택해도 완료 세트와 미완료 세트를 구분해 보존한다. 명시적 “기록 버리기”만 현재 폐기 경로를 사용한다. |
| 기기 재부팅 | 부팅 전후 센서 시간축을 분리하고 원본을 이어 붙이지 않는다. 기존 `separateSensorBoot()`의 보존 방향을 유지한다(`W/WearWorkoutService.kt:884–904`). |
| 업데이트 설치·앱 교체 | 설치 전 운동이 끝났고 미완료 저장이 없는지 확인한다. 새 버전은 복구와 스키마 검증을 먼저 수행한다. 설치 성공 callback과 실제 설치 버전, 운동 기록 복구 성공을 각각 확인한다. |
| 다운로드·설치 실패 | 기존 운동 데이터는 유지하고 업데이트 상태만 재시도 가능하게 둔다. OS 설치 상태를 확인하기 전 성공·실패를 추측하지 않는다. 공간 확보를 위해 미ACK 운동 원본을 자동 삭제하지 않는다. |
| 폰·워치 버전 혼용 | 앱 버전 일치 대신 프로토콜·기능 지원·저장 형식 호환성을 판단한다. 미지원 기능은 차단하고 pending 기록을 보존한다. 응답하지 않은 명령을 적용 성공으로 처리하지 않는다. |

워치에는 이미 기능 지원을 주고받는 코드가 있고(`W/WatchWorkoutOutbox.kt:12–25`), 폰 스냅샷 디코더는 과거 스키마를 읽는 분기가 있다(`C/WorkoutSnapshot.kt:177` 이후). 그러나 이것이 모든 신구 조합의 호환성을 뜻하지는 않는다. 다음 배포 전에는 최소한 **새 폰/직전 워치, 직전 폰/새 워치, 둘 다 새 버전**에서 현재 세트와 휴식 제어가 보존되는지 확인해야 한다.

문제 버전을 되돌릴 때 “직전 APK를 설치하면 된다”는 절차는 부적절하다. Android는 일반적으로 낮은 `versionCode` 설치를 막는다. 이전 동작을 복원한 **더 높은 versionCode의 복구 릴리스**가 기본 대안이며, 이미 저장된 새 스키마를 읽을 수 있어야 한다. 삭제·재설치를 기본 복구법으로 삼지 않는다. [Android 버전 관리 계약, 확인 2026-10-18](https://developer.android.com/studio/publish/versioning)

**7. 플랫폼 계약이 주는 한계**

- `START_STICKY`는 시스템의 재생성 시도를 요청한다. 즉시 재시작이나 중단 없는 센서 측정을 보장하지 않는다. 워치의 조건부 `START_STICKY`(`W/WearWorkoutService.kt:724`)를 복구 완료 증거로 취급하면 안 된다. [Service 계약, 확인 2026-10-18](https://developer.android.com/reference/android/app/Service)
- Wear `MessageClient`에는 지속 저장과 자동 재시도가 없다. 현재 앱의 outbox·ACK·중복 방지는 필요한 설계다. 전송 성공만으로 상대 저장 완료를 판단하지 않는다. [Wear Data Layer 클라이언트 계약, 확인 2026-10-18](https://developer.android.com/training/wearables/data/client-types)
- Android 15 이상을 대상으로 하는 `dataSync` FGS에는 백그라운드 실행 시간 제한이 있다. 폰은 `onTimeout()`에서 서비스를 멈추며 상태를 남긴다(`P/PhoneWorkoutService.kt:89–93`). 워치는 `health|dataSync` 선언과 실제 활성 타입을 대조하고 타임아웃 처리를 확인해야 한다. 기기의 OS와 이 제한에 실제 도달하는지는 미확인이다. [FGS 시간 제한, 확인 2026-10-18](https://developer.android.com/develop/background-work/services/fgs/timeout)
- body sensor를 사용하는 `health` 서비스의 백그라운드 시작에는 권한 제약이 있다. 워치 manifest에는 `BODY_SENSORS`가 있지만 background 센서 권한은 없다. 모든 재시작이 실패한다는 뜻은 아니며, 서비스 재시작 방식과 권한 상태별로 구분해야 한다. [FGS 타입·권한 계약, 확인 2026-10-18](https://developer.android.com/develop/background-work/services/fgs/service-types)
- `USER_ACTION_NOT_REQUIRED`는 설치 확인 생략 요청이며 OS 조건에 좌우된다. 새 설치 코드만 보고 삼성 화면·Play Protect·실제 교체 시간을 보장할 수 없다. [PackageInstaller 계약, 확인 2026-10-18](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams)
- `ApplicationExitInfo`는 Java 크래시·네이티브 크래시·ANR 등을 구분하는 데 도움이 된다. 종료 원인이 곧 원인 라이브러리를 특정해 주지는 않으므로, MediaPipe 책임 여부는 스택·발생 화면·재현 자료를 함께 확인해야 한다. [ApplicationExitInfo 계약, 확인 2026-10-18](https://developer.android.com/reference/android/app/ApplicationExitInfo)

이 자문이 권고하는 첫 변경 묶음은 **기록을 버리는 종료와 화면 닫기의 분리, 설치 commit의 운동 상태 차단, 워치 저장 실패 경계 보강, 양쪽 복구 관측**이다. ABI 제한은 별도의 작은 변경으로 진행하고, 프로세스 분리는 그 이후에 확보한 장애 근거로 결정하는 것이 적절하다.
