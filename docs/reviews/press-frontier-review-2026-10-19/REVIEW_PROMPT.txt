숄더프레스 자동 횟수·진동 측정에 대한 독립 기술 자문을 요청한다.

이전 AI의 결론을 확인해 주는 역할이 아니다. 현재 엔진이 최선이라는 근거가 없어서 검토를 요청한다. 하이브리드가 정답이라는 가정도 하지 말고, 기존 설계·실험·측정 지표 자체부터 의심해 달라. 이 범위만 검토한다: 손목 센서 기반 숄더프레스 카운트, 실제 반복과 진동 시점, 세트 종료, 세트 후 재분석. 앱 전체 UI·운동 처방·다른 종목 개편은 범위 밖이다.

[실제 목표와 사용자 불만]
Galaxy Watch8과 Android 폰을 쓰는 개인 운동 앱이다. 사용자가 원하는 1회는 “팔을 ㄴ자로 준비 → 위로 밀기 → 처음 ㄴ자 위치로 복귀”다. 복귀할 때 한 번 진동해야 한다. 실제 스미스 숄더프레스에서 횟수가 과다 기록되고 “진동박자가 지맘대로” 어긋난다고 한다. 스크린샷에는 목표 10회에 완료 기록 24회가 보이지만, 그 실전 세트의 실제 수행 횟수·원본 센서는 아직 확보하지 못했다. 목표 10이 실제 수행 10의 증거는 아니다.

이전 AI는 공개 데이터 점수, 맨손 촬영에서 총 10회 일치, 실제 중량 운동에서의 정확도, 복귀 순간 진동을 충분히 구분하지 않았다. 사용자는 “좋은 논문이 있는데 왜 먼저 가져다 구현하지 않고 직접 촬영과 자체 수직 엔진 실험부터 했느냐”고 지적했다. 이 지적도 평가해 달라. 단순히 더 찍으라는 답으로 책임을 넘기지 말고, 현재 자료로 할 수 있는 분석부터 제안해 달라.

[엔진 명칭: 혼동 금지]
A = 옛 혼합 가속도·자이로 엔진: press-return-family-v4.
B = ‘새 엔진’: vertical-press-return-family-v1. 중력 방향 가속도 투영, 느린 바이어스 제거, 누설 적분 및 평활로 얻은 signed velocity proxy에서 올림/내림 쌍을 감지한다. 물리적 높이·관절각·진짜 속도를 직접 측정하지 않는다. 내려가는 신호가 음의 극값에서 절반 회복했을 때 반복을 닫을 수 있다.
C = ‘새새 엔진’ 실험 후보: B의 복귀 회복 비율 0.50을 0.15로만 변경했다. 전체 구조·다른 제한은 그대로다. 테스트 전용이며 앱에 적용하지 않았다.
D = 이번에 구현한 MM-Fit 논문 설명 기반 오프라인 재현본. 저자 원본 코드나 0.18회 오차의 정확한 재현이 아니다. 아래 제한을 읽어라.
카메라 실시간 카운터는 또 다른 경로다. UpperBodyPoseCounter는 숄더프레스에서 팔꿈치 각도 기준을 쓴다. 카메라가 잘 셌다는 사실을 워치 엔진 성공으로 간주하면 안 된다.

[확인된 적용 상태]
B는 원래 덤벨 숄더프레스 ID에만 연결됐고 스미스 ID는 A에 남아 있었다. 두 제공 ZIP의 frozen profile도 A다. 스미스를 B에 연결하고 과거 A 프로필을 재생할 수 있게 하는 수정은 로컬 커밋됐으나 배포되지 않았다. C·D도 미배포다. 기존 공개 APK에서의 실전 과다 카운트가 B 또는 C 때문에 일어났다고 단정할 수 없다. 복원된 진행 중 세트는 frozen profile을 유지할 수 있다. 개인 패턴·준비 게이트·서비스 상태가 실제 적용에 끼치는 영향도 검토 대상이다.

[현재 증거]
1. 같은 MM-Fit 변환 자료의 숄더프레스 60세트. 원래 시각·관측된 샘플·같은 label start/end를 사용한다. 기존 A/B/C 평가는 실제 자이로 시각에 가장 최근 가속도를 결합한 약 100Hz 입력이다. 합성 정지 샘플, 목표 횟수로 강제 종료, 끝에서 임의 반복 추가는 없다. 이 자료는 이미 개발 중 여러 번 살펴본 데이터여서 독립 미사용 검증이 아니다.
- A: MAE 4.833회, 정확한 세트 합계 4/60, ±1회 이내 8/60.
- B: MAE 0.667회, 정확히 25/60=41.7%, ±1회 이내 55/60=91.7%.
- C: MAE 0.867회, 정확히 13/60=21.7%, ±1회 이내 55/60=91.7%.
‘정확히 일치’는 세트 합계 일치율이며, 개별 반복 감지율·정밀도·진동 위상 정확도가 아니다.
B는 30세트에서 1회, 5세트에서 2회 부족했고 이 평가에서 과다 카운트는 없었다. 실제 앱의 과다 카운트와 방향이 다르다.

2. C가 B보다 1회 더 놓친 12세트는 label 끝에서 마지막 후보가 진행 중이었다. 실제 뒤 2초 센서를 읽는 별도 진단에서 7세트는 마지막 판정이 나왔다. 3세트는 3초 lobe 제한에 걸려 후보가 폐기됐고, 2세트는 해당 관측 구간에서 계속 미완료였다. 뒤쪽 데이터가 없는 것은 아니다. B도 24세트에서 label 안에 시작한 후보가 label 뒤 2초 안에 닫혔다. 이 진단을 기존 점수에 몰래 합치지 않았다. label 경계·시간 초과가 원인 후보라는 증거지, 실제 복귀를 정확히 놓쳤다는 사람 확인 정답은 아니다. 임의의 앞 2초를 prefeed한 뒤 counting reset하는 실험은 오히려 크게 악화돼 채택하지 않았다.

3. 사용자가 제공한 ZIP 두 개는 실제 스미스 중량 세트가 아니라 집에서 앉아서 맨손으로 수행한 프레스 동작이다. 사용자는 각 10회라고 확인했다. 첫 ZIP에는 총횟수 10의 저장된 사용자 확인이 있고 둘째는 저장된 확인 횟수 필드가 비어 있다. 반복별 시작/상단/복귀 시각의 사람 확인 라벨은 없다.
- 센서 1,484개 / 1,467개, 약 50Hz, 약 29.69초 / 29.35초. 내보내기 해시와 기본 메타데이터 검사 통과.
- A와 B 모두 두 파일 합계는 각각 10회지만 이벤트 시각은 다르다. A 간격은 최대 5.51초 및 최소 1.26초까지 불규칙하고 B는 약 2.1–2.5초다. 간격이 일정한 것이 물리적 복귀 정확도를 증명하지는 않는다.
- C도 두 파일에서 10회씩 세고, B보다 판정이 약 0.11–0.28초 늦어진다. 늦어졌다는 사실만으로 개선이라 판정하지 않았다. 센서↔영상 시계 정렬 오차와 실제 진동 실행 지연도 고려해야 한다.
- 개인 영상·원본 센서 ZIP은 이 일반 자문 묶음에 포함하지 않았다. 필요하면 사용자에게 어떤 파일/라벨이 필요한지 구체적으로 설명하라. 제공받지 않은 영상을 봤다고 하거나 경계를 검증했다고 주장하지 말라.

4. MM-Fit 논문 표 7은 왼손 워치 가속도 숄더프레스 MAE 0.18회를 보고한다. 지금 실험과 전처리·세트 경계·구현 설정이 같다고 확인되지 않았다.
D는 논문 4.4절의 표준화→3차 SG→첫 PCA→피크 거리 억제→국소 자기상관 기반 주기→0.75주기 주변 작은 피크 제거→피크 진폭 40백분위수 절반 미만 제거를 구현했다. 공개 기본 저장소에서 원래 카운터 코드는 찾지 못했다. SG 길이·종목별 최소/최대 시간·자기상관 창 길이·PCA 부호 등 미명시 설정은 자체 가정이다.
- 고정 가정: 50Hz 근처 실제 샘플 선택, SG 0.5초, 반복 0.6–8초, 자기상관 창 ±8초. 타깃 횟수나 영상을 입력하지 않는다.
- PCA 부호는 최대 절대 loading이 양수인 방향으로 고정. 세트마다 정답에 맞게 부호나 센서를 고르지 않는다. 다른 부호/센서 결과도 공개한다.
- D 가속도/고정 양방향: MAE 0.500, 정확히 34/60=56.7%, ±1회 이내 56/60=93.3%. 반대 부호 가속도는 28/60, MAE 0.667. 자이로는 각각 16/60, MAE 1.483 및 20/60, MAE 1.300.
- D 가속도/고정 방향은 두 개인 ZIP에서 10회·11회. 파일마다 부호를 바꿔 둘 다 10회로 만들지 않았다.
- 세트 전체 표준화·PCA·진폭 순위·중심 창 자기상관·전체 백분위수는 미래 관측을 사용한다. 그대로는 즉시 확정되는 실시간 진동 엔진이 아니다.
- 기존 PaperPeakRepAnalyzer는 다른 논문(Prabhu et al., 2020)을 참고한 변형 코드다. D와 혼동하지 말라.

[실행 경로에서 주의할 것]
실제 운동 서비스는 센서 후보를 감지하면 recordDetectedRepAt에서 reps를 늘리고 checkpoint 후 로컬 워치 진동을 호출한다. 일반 rep tick은 35ms, 목표 도달에는 별도 진동 패턴이 있다. 엔진 자체, 준비/복원/패턴 선택, 센서 sample 시각과 callback 도착 차이, 영속 저장, 진동 실행의 문제를 구분하라. 모든 불규칙 진동을 무조건 필터 문턱 탓으로 돌리지 말라.
일반 운동, 옛 calibration, paired reference는 준비 보존·목표 도달 종료 정책이 다르다. SetEndGate와 검출기 lobe 시간 제한, 카메라의 10회 후 3초 종료도 서로 다른 코드다. ‘3초’가 같다고 같은 타이머라고 생각하지 말라. 실제 운동은 목표 도달 즉시 종료하지 않는 정책이 이미 있으니, 없는 버그를 가정해 새 기능으로 제안하지 말라.

[열어둔 설계 공간]
현 상태 유지, B 적용 후 검증, 논문 방법 재현 보완, 다른 신호처리/학습/상태추정 방법, 조건부 수동 전환, 실시간+사후 하이브리드, 또는 다른 구성을 모두 검토할 수 있다. 아래 하이브리드는 사용자의 아이디어이며 채택 결정이 아니다.
- 실시간 경로는 복귀 순간 진동과 임시 횟수에 집중.
- 세트가 끝난 뒤 휴식 중 전체 원본으로 횟수/구간을 다시 분석해 최종 기록을 결정.
하이브리드가 불필요하거나 문제가 더 크면 명확히 반대해 달라. 두 엔진을 평균내거나 사후 엔진을 무조건 정답으로 삼는 것은 요구사항이 아니다.

[당신에게 요청하는 독립 검토]
A. 먼저 앞선 설명/코드/실험에 오류·과장·틀린 비교가 있는지 감사하라. 0.18과 0.500/0.667을 어떻게 비교해야 하는지, 이 ‘설명 기반 재현’이 실제로 논문을 충실히 따르는지도 직접 확인하라. 평가 세트 경계를 바꾸면 무엇을 검증하는지가 달라지는지 설명하라.
B. B→C 악화를 경계 잘림·시간 초과·신호 추정·다른 원인으로 나누고, 현재 근거로 확정할 수 있는 범위를 정하라. 버그인지 설계 한계인지 가르는 가장 작은 재현 실험을 제시하라.
C. 실전 과다 카운트와 불규칙 진동의 원인 가설을 우선순위화하고, 각 가설을 반증할 로그/실험을 제시하라. 원본이 없는 24회 세트를 진단 완료했다고 하지 말라.
D. 최소 세 가지 실질적으로 다른 대안을 비교하라. 현 프레이밍을 깨는 대안도 포함하라. 왜 하이브리드가 적절하거나 부적절한지, 단일 실시간 엔진·사후 전용·다른 논문 접근보다 실제로 유리한 조건을 논하라.
E. 추천안은 구현 가능한 설계로 제시하라. 하이브리드라면 실시간/사후의 책임, 입력 버퍼와 시간 축, 종료 유예와 원본 보존, 잠정→최종 상태, 중복/누락 매칭, 수동 수정 우선권, 실패·미완료·연결 끊김·프로세스 재시작 복구, 배터리/메모리/지연을 구체화하라. 단순한 구조도나 두 엔진을 붙이라는 답으로 끝내지 말라. 다른 설계가 낫다면 그 설계를 같은 수준으로 제시하라.
F. 논문/공개 구현/다른 인터넷 자료를 필요에 따라 직접 찾아라. 최초 논문·저자 코드·실제 구현·독립 실험을 구분하고 링크하라. 실시간/오프라인, 센서/장착 위치, 데이터/분할, 실험실/중량 실전, 합계/반복 경계/지연 지표를 비교하라. ‘논문 그대로면 Watch8에서 더 정확하다’거나 ‘현재 B가 최선’이라는 보장이 있는지 명시적으로 답하라. 웹에 접근할 수 없다면 그 한계를 밝혀라.
G. 검증 프로토콜을 내라. 실제 시계의 연속 센서를 시각순으로 처리하고, 미래 데이터를 사용하는 경로는 따로 표시하라. 개발용과 평가용 세션/사람을 분리하고 목표 횟수·세트 길이·사람 라벨 누출을 막아라. 총횟수 exact/MAE뿐 아니라 개별 rep precision/recall, 실제 복귀 대비 판정·진동 지연 분포, 추가 동작 오인식, 수정 빈도/사후 보정 크기·시간을 평가하라. 합리적인 통과·중단 기준은 이유와 함께 제안하되, 근거 없는 99% 보장을 만들지 말라.
H. 추가 촬영이 필요한지와 가치가 높은 최소 촬영 계획을 제시하라. 맨손 반복만 더 받는 것으로 충분한지, 스미스/덤벨·중량·속도·중간 정지·내려놓기를 어떻게 구분할지, 언제 촬영을 멈출지도 정하라. 평소 운동보다 위험한 수행은 요구하지 말라. 이미 가진 영상 20회의 복귀 라벨을 먼저 만드는 것과 새 자료 수집 중 무엇부터 할지 판단하라.
I. 마지막에 가장 작은 우선 구현 순서, 파일/함수 단위 변경안과 롤백 조건을 내라. 앱 전체 재작성이나 대규모 ML 학습이 필요한지부터 따져라. 지표 개선만으로 실제 체감 개선이라고 선언하지 말라.

처음에는 비전문 사용자도 이해할 수 있게 “무엇이 확인됐고 무엇이 틀렸으며 무엇을 먼저 할지”를 짧게 설명하라. 그 다음 근거·대안 비교·구체적 설계·검증 실험·최소 코드 변경안을 제시하라. 사실/추론/제안/미확인을 분리하고, 이전 AI의 설명이나 하이브리드 아이디어에 동의하는 것으로 답을 시작할 필요는 없다. 무조건 새 엔진을 만들거나 추가 촬영을 요구하는 결론으로 몰지 말라.
