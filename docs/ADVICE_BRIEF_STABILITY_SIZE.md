# 고성능 모델에게 보낼 브리프: 운동 앱의 안정성과 크기

아래 블록을 그대로 복사해서 GPT Pro, Claude Opus, Gemini 등에 보낸다. 답을 받으면 모델 이름을 가리고 같은 기준으로 비교해서 좋은 부분을 합친다.

```text
너는 모바일/웨어러블 앱 신뢰성 컨설턴트야. 아래 앱의 안정성과 앱 크기 문제를 독립적으로 비판하고, 서로 다른 설계안을 비교해서 가장 현실적인 안을 권고해줘. 내 현재 생각에 맞춰주려고 하지 마. 전제가 틀렸다고 보이면 그렇게 말해줘.

## 앱과 사용자
- 개인용 근력운동 기록 앱 "워치짐". 안드로이드 폰 앱(Kotlin, Jetpack Compose + 일부 View)과 Wear OS 워치 앱(Kotlin, 순수 View, 센서와 심박은 워치에서 측정). 둘은 Wear Data Layer 메시지로 통신한다. 개발자 한 명(비전문 개발자, AI 에이전트로 개발)이고 사용자도 본인 한 명이다. 기기는 폰 1대와 Galaxy Watch 계열 1대.
- 배포는 GitHub Releases에 APK를 올리고 앱이 `update-phone.json`/`update-watch.json`을 읽어 앱 안에서 업데이트한다. 서명 키는 로컬 Mac에 있다.
- 워치는 가속도/자이로로 반복 횟수를 세고, 폰은 보정용으로 카메라(MediaPipe Tasks Vision, 포즈 랜드마커 lite)를 쓴다.

## 사용자의 불만(직설)
"점점 워치랑 폰 앱이 비대해지는 게 문제다. 적당히 안정적인 앱을 만들고 싶다. 튕기는 일도 줄이고 싶다. 운동 중에 튕기는 게 100번에 한 번이라도 나면 바로 삭제하고 쌍욕 박는다."

## 성공 기준
- 운동 중(세트 측정, 휴식 타이머, 폰-워치 동기화) 앱이 비정상 종료해도 그 세트의 기록이 보존되고 자동으로 이어진다. 사용자가 체감하는 "튕김"이 사실상 없다.
- 기능 추가 속도를 크게 떨어뜨리지 않는다.
- 폰 APK는 불필요하게 크지 않다.

## 지금 알고 있는 것(직접 측정, 2026-10-18)
- 폰 APK 57.8MB, 워치 APK 1.3MB. 폰의 `libmediapipe_tasks_jni.so`가 CPU별로 arm64 10.0MB, armeabi-v7a 7.1MB, x86 14.3MB, x86_64 12.4MB 들어 있다. 포즈 모델 5.5MB, `classes.dex` 4.4MB. R8 코드/리소스 축소는 켜져 있다.
- 코드 집중: 폰 `MainActivity` 3,156줄, 워치 `WearWorkoutService` 2,299줄(측정 서비스, 핵심 경로), 워치 `MainActivity` 1,095줄.
- 워치 측정 서비스에 `check(` 28개, `require(` 32개, `!!` 7개, `getOrThrow` 5개. 서비스 상태는 디스크에 체크포인트하고 재시작 시 복원하는 코드가 있으며, 폰은 `ApplicationExitInfo`와 전역 예외 처리기로 진단 파일을 남긴다. 워치에는 그 둘이 없다.
- 폰의 카메라/MediaPipe(네이티브)는 운동 앱과 같은 프로세스에서 돈다. 워치 서비스와 화면의 프로세스 분리 여부는 확인하지 않았다.
- 단위 테스트(코어, 워치 Robolectric, 폰 Robolectric)는 많이 있다(약 900개). 실기기 장시간 테스트나 카오스 테스트는 없다.

## 모르는 것
- 실제로 얼마나 자주, 무엇 때문에 튕기는지(현장 데이터 없음).
- 자동 업데이트가 운동 중에 설치되는지.
- 위의 `check/require/!!`가 실제 운영에서 몇 번 던져지는지.

## 비판하고 도전해도 되는 설계 공간
- 프로세스 분리, "fail fast vs 기록 보존" 정책, 크래시 후 자동 복구, 워치-폰 역할 분담(워치 단독 동작 범위), 앱을 쪼개거나 합치기, 카메라 기능을 별도 앱/모듈로 빼기, 네이티브 라이브러리 CPU 제한과 모델 크기, 업데이트 배포 안전장치, 큰 파일 리팩터링 vs 두기.
- 이 중 무엇이 핵심 레버이고 무엇이 과투자인지 판단해줘. 내가 틀렸다고 보이는 가정이 있으면 지적해줘.

## 요청하는 결과물
1. 가정과 증거의 허점 비판(가장 위험한 미확인 사항 우선).
2. 서로 확실히 다른 설계안 최소 3개(하나는 내 문제 틀 자체에 도전하는 안). 각각 효과, 비용, 위험, 한 명의 개발자가 AI 에이전트와 할 수 있는 현실성을 비교.
3. 하나를 권고하고 이유를 설명. 작업 순서와 각 단계의 "끝났다고 볼 기준".
4. 검증 하니스: 튕김 없음을 어떻게 증명/측정할지(지표 정의, 목표 수치, 장시간/카오스 테스트 설계, 현장 텔레메트리 최소 설계).
5. 실패 복구 절차(배포한 버전이 문제일 때, 서비스가 죽었을 때, 워치와 폰 버전이 섞였을 때).
6. 지금 코드에 바로 적용할 수 있는 최소 변경 목록(파일 단위가 아니라 개념 단위로).
7. 안드로이드/Wear OS/MediaPipe의 최신 동작이나 제한이 권고에 영향을 주면, 확인한 공식 출처와 날짜를 붙이고 확인 못 한 건 "미확인"이라고 적어줘.
```
