# 다음에 할 일 (2026-10-18 기준)

2026-10-18 사용자 범위 조정: "너무 호들갑아님? 누가 운동중에 업데이트를 누르냐". 수동 OTA와 운동의 상호 잠금은 제외하고 디자인·저장 실패 경계·워치 로컬 종료 진단에 집중한다. 추가했던 OTA 변경과 테스트는 제거했다. [소스 구현·차단 근거·주 에이전트의 좁은 검증 목록](reviews/2026-10-18-sol61-high-implementation.md)을 먼저 본다.

## A. 안정성과 용량 (경민의 기준: 운동 중 100번에 1번이라도 튕기면 삭제)

초기 조사 스냅샷(2026-10-18 구현 전 코드와 기존 APK에서 확인한 값; 아래 소스 변경/검증 상태와 구분)
- 폰 APK 57.8MB, 워치 APK 1.3MB. 폰의 MediaPipe 네이티브 라이브러리가 약 44MB이고 CPU 4종(arm64 10.0, arm32 7.1, x86 14.3, x86_64 12.4MB)이 다 들어 있다. 포즈 모델(`pose_landmarker_lite.task`) 5.5MB, `classes.dex` 4.4MB. R8 축소는 이미 켜져 있다.
- 큰 파일: 폰 `MainActivity` 3,156줄, 워치 `WearWorkoutService` 2,299줄, 워치 `MainActivity` 1,095줄.
- 워치 `WearWorkoutService`에 `check(` 28, `require(` 32, `!!` 7, `getOrThrow` 5. 조건이 깨지면 예외가 던져져 측정 서비스가 죽을 수 있는 경로다(전부가 위험하다는 뜻은 아님, 감사가 필요).
- 폰은 `LocalExitDiagnostics`(전역 예외 처리기 + `ApplicationExitInfo`)가 있고 워치엔 없다.
- 폰의 보정 카메라(MediaPipe 네이티브)는 운동 앱과 같은 프로세스다(`android:process` 없음).

모르는 것
- 실제로 얼마나 튕기는지(현장 데이터 없음), 무엇이 원인인지.
- 기존 수동 설치가 요청 후 어떤 시점에 실행되는지는 실기기 미확인이다. 이번 안정성 작업의 우선 대상으로 확대하지 않는다.

당초 자문 후보(현재 구현 여부·최신 범위는 아래와 구분)
1. 릴리스 빌드 CPU를 arm64로 제한(약 40MB 감소 추정). 에뮬레이터용 디버그는 유지.
2. 워치 전역 예외 처리기와 종료 원인 기록, 서비스 자동 복구.
3. 운동 중 경로의 `check/require/!!`를 "기록 보존 + 경고"로 바꾸는 감사.
4. 폰 보정 카메라를 별도 프로세스로 분리, 워치 측정 서비스와 화면의 프로세스 분리 검토.
5. 센서 폭주, 서비스 강제 종료 후 복구, 연결 끊김 반복의 장시간 스트레스 테스트와 "세트 중 비정상 종료 횟수" 기록.
6. 운동 중 업데이트 설치 차단, 직전 APK로 되돌리기: 최신 사용자 판단으로 이번 범위에서 제외.
7. 큰 파일을 기능 단위로 쪼개기, 안 쓰는 경로(옛 보정, 섀도 검출기 등) 제거.

2026-10-18 자문 수신: Codex2의 **Astra High**로 읽기 전용 검토를 받았다. [자문 원문](reviews/2026-10-18-astra-high-stability-size-advice.md)과 [실행 확인·검토 메모](reviews/2026-10-18-astra-high-stability-size-notes.md), [요청 브리프](reviews/2026-10-18-astra-stability-size-request.md)를 저장했다.

자문 원문은 독립 의견으로 보존한다. 사용자 승인 후 워치 청크/체크포인트 실패 반환, 원본·식별자 보존, 센서·타이머·서비스 예외 경계, 제한된 로컬 종료 진단을 소스로 구현했다. 작업자 소켓 제한 후 주 에이전트가 현재 트리를 컴파일하고 대상 테스트 14개(저장/진단/복구 12개, 세 화면 렌더 1개, 정지·재개 모핑 1개)를 통과시켰다. 설치/운동 상호 잠금은 사용자가 과하다고 판단해 새 구현을 모두 제거했다. 프로세스 분리·대규모 리팩터링은 하지 않는다. 최근 앱 닫기·명시적 강제 종료의 폐기 결정도 그대로 유지한다. 원래 브리프는 `docs/ADVICE_BRIEF_STABILITY_SIZE.md`에 유지한다.

ABI는 기존 OTA APK만 읽었다(폰 60,607,320 bytes, 워치 1,351,831 bytes). 폰에는 arm64-v8a·armeabi-v7a·x86·x86_64가 남아 있다. 주 에이전트 ADB에는 연결 기기가 없어 물리 기기 ABI를 확인하지 못했으므로 필터를 추가하지 않았다. 향후 연결 가능한 실제 폰의 `ro.product.cpu.abilist`와 개인 배포 대상 목록을 확인한 뒤 별도 변경으로 판단한다. 새 빌드·용량 재측정은 하지 않았다.

## B. 이번 대화에서 남은 것

- 실기기 확인: 휴식 4a·정지 모핑, 측정 1-B, 시작 3초 정지, 7초 세트 종료 대기, 폰·워치 휴식 시간 동기화와 워치 정지·재개, 새 졸라맨, 보정 카메라 개선.
- 폰의 휴식 정지 중 건너뛰기(워치 요청)가 폰 화면에서 어떻게 보이는지 직접 확인.
- 폰과 워치를 같이 업데이트하지 않았을 때(워치만 새 버전) 워치 정지 버튼이 옛 폰에서 어떻게 되는지 확인.
- 세 화면과 옛 회색은 소스/기존 렌더 대조 후 수정했다. `WatchDesignFinishTest` 현재 트리 렌더와 웹폰트 로드 후 동일 값 시안 비교도 완료했다. Android/웹 한글 글리프와 바깥 케이스 차이는 구분한다.
- 휴식 정지 중에도 최근 심박을 보여줄지(센서를 켜두면 배터리 소모) 결정.
- 시안에서 쓰지 않은 휴식 4b·4c와 전용 스타일/선택 문구는 정리했다. 4a·정지 모핑의 현재 트리 대상 테스트도 통과했다.

2026-10-18 최신 디자인: 사용자가 제공한 심박 화면 사진 기준으로 상단 운동 시간·완료 세트, 중앙의 큰 심박수, 아래 Zone N, 하단 반원 게이지/흰 점을 구현했다. 중앙 큰 바와 Q–T 시안은 대체됐다. 320ms 전환과 1~5존/같은 존 심박 변화/빠른 연속 변경/미수신 대상 검사 및 렌더 확인 완료. 실기기 확인 목록에 이 전환도 포함한다.

## C. 출시 마스터플랜 (2026-10-18 논의, 큰 방향만)

지금은 측정 정확도·엔진·디자인 완성이 먼저다. 여러 종목의 횟수 인식이 아직 부정확하고, 아래 단계는 그 뒤에 한다.

- **1차 · 안드로이드 베타 출시:** 한 레포 안에서 빌드 종류를 `dev`(GitHub 배포, 내가 받는 용·자체 업데이터 유지)와 `store`(사용자용)로 나눈다. `store`에는 광고, 약관, 첫 설치 안내 탭, 소셜 로그인, 개인정보처리방침, 권한 설명, 건강 데이터 선언을 넣고 `REQUEST_INSTALL_PACKAGES`와 자체 업데이터는 뺀다. 비공개 테스트로 올리고 바이럴을 돌린다. 신규 개인 계정이면 12명 14일 비공개 테스트가 필요하다(계정 생성일 미확인).
- **베타 혜택:** 프로 구독 비교표(무료/프로/베타 유저, 기능별 ○·×)를 보여주고 베타 유저 칸은 프로와 같게 전부 ○. "베타 기간 한정 무료"로만 표기하고 평생·서비스 기간 같은 약속은 하지 않는다. 정식 출시 때 베타 유저 칸만 빼면 정식 요금표가 된다. 프로 기능은 "베타 중 무료" 플래그 하나로 켜고 끈다.
- **수동 측정 종목:** 풀업, 레그프레스처럼 손목 인식이 안 되는 종목은 정식 출시 때도 수동이다. 앱 안에 "손목 자동 측정이 어려워 직접 입력하는 운동"이라고 명시한다(현재 표시 문구 유무는 미확인). 근거는 `EXERCISE_MEASUREMENT_MATRIX.md`의 M 수동.
- **1.5차 · 수익화:** 반응과 이용자 증가가 확인되면 유료 구상, 광고 여러 개가 안정적인 수익이 되는지, 사용자 개인정보 보관 방식을 정한다. 내 서버는 사실상 없어서 유지비는 코딩 구독뿐이다.
- **2차 · iOS(+애플워치):** "아이폰용도 내주세요" 같은 피드백이 쌓이면 시작한다. 공유 로직은 Kotlin Multiplatform, 워치 화면은 SwiftUI가 현실적이다. Xcode와 실제 애플워치가 필요하다.
